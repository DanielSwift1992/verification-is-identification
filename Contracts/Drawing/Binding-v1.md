# World drawing binding

`drawing-binding/1` is an ordinary pinned owner input. Its `roles` supply paints for each theme and an optional portable sRGB projection, `registers` supply faces, `layout` supplies the named measurements, `shadow` supplies its paint and opacity, and `leafCountBases` supplies opaque one-leaf readings. A layout row has either a textual reading or a Swift type expression. Native Swift compiles the expression; the JS port reads its existing arithmetic subset. Missing readings refuse by binding field and world root. An unavailable expression remains outside the port's supported subset.

DocumentKit defines the rendering relations and the required `DrawingStyle` / `StyleKeys` places. The owner declares its additional requirements in a separate Swift protocol inheriting `DrawingStyle`. The record's `styleContract` names that protocol, its owner-relative source input and SHA-256. A delivered profile also declares the source's input row. The source is compiled as a separate file together with the generated Binding; the Binding explicitly conforms to the named owner protocol. The projector never derives that protocol from the supplied layout values. A missing required witness refuses at the compiler even when the drawing does not use that key. These constraints establish conformance, not the content of an arbitrary overridden `typeName`.

The owner can supply a generated companion with `--aliases`. It exposes the owner's own axis names within the compilation context and supplies `StyleBound.Binding` there. The world's source and imports remain the same. Each such compilation context selects one owner; explicit bindings can be compiled together without installing global companion aliases. The companion, requirement source and source JSON are declared context inputs. SDK paint names are unfilled CSS slots: a library can forward them before choosing an owner. `DeliveredSVG` resolves those slots through the selected Binding at the reading root. The shared footer declares the same slots for HTML. The owner record also declares any `CardPalette` instances; the projector does not choose their paints.

`DrawingPalette` is the shared role vocabulary for figures. Its foreground/paper pairs have an owner `ReadablePaintPair / LegiblePaintPair` whose proof has the two numerical sides. Native labels check that equality. The figures bind those roles to the pinned gate palette; the generic contract fixture takes the same owner palette and registers. Register and glyph projections are checked against their pinned and measured inputs.

The portable SVG attribute precedes the owner's exact CSS paint in the style declaration. Values come from the binding. The Swift and JS readers use the same delivery rule. Owner profile receipts carry the exact binding and its input row, so serve and publication select one record. The reader does not construct a company palette or execute a generator.

## Syntactic style law

`Checks/drawing-binding.py` visits Swift recursively, DocC Markdown and the shared footer template. `Scripts/style-literals.py` checks literal values at SVG/CSS paint, face, font size/weight, stroke, radius, marker and opacity positions. It folds adjacent string pieces and follows simple local scalar and typeName literals at this edge. Concrete non-generic Paint declarations are refused in any inheritance-list order. Cover and weight vocabulary carries no selected scalar. The law does not evaluate arbitrary Swift programs. Numerical algorithms, ordinary prose such as Inter-world or #abc, role references and SMIL's fill=freeze timing policy remain outside this syntactic class. Native projection, register, contrast and byte-parity laws check the actual readings separately.

`Scripts/footer-check.py` parses every generated footer as HTML, then checks each script with the JavaScript parser. Both hooks and their owner substitutions are required. The broken-comment control exercises the HTML boundary before JavaScript parsing.

Historical names such as R10, R12 and Cover06 identify roles; their spelling does not constrain the owner's numeric choice. The accompanying Swift input supplies their values and the original generic composition names. No world source or import needs to be edited to select that input.
