# Context names v1

These finite questions extend the existing context reader with supplied module re-exports and qualified nominal heads, including the ground generic applications supported by context/2. An actual `@_exported import` supplies an export edge. Its transitive closure extends each source's declared imports. An ordinary import in another module supplies no export edge. The context still binds each original input and hash; the source view resolves nominal identities before definition reduction.

A local declaration and an imported declaration can have the same short spelling. `M.N` selects N in the available module M. Two imported candidates used without qualification refuse at the reference. Two declarations in one module refuse at their source addresses. Bare alias cycles refuse at the alias declaration. Existing unqualified collision admission remains unchanged where no source supplies qualification and no imported reference requires an ambiguity choice. A qualified generic application requires context/2, exact declaration arity and applicability grounds. Declared bounds use the existing generic membership derivation through an unconditional conformance; a missing path refuses. Bound parameters/axes and module qualifiers spanning lines remain outside this extension. This is a fragment of Swift name resolution.

The internal nominal symbols are fresh relative to every supplied read view. Their serials distinguish declarations; their module/name suffixes identify them in diagnostics. They are not declarations added to the source or aliases supplied by an operator. Original source bytes, contexts and their hashes remain the input roster. The same scalar identity used by the common Court lexer keys module edges and declaration identities.

`contract.json` is read by the existing `Checks/court-contract.py` law. Its compiler plan assigns exactly the judged source files to named modules and a primary module. The driver checks that assignment against the context, emits the borrowed modules, then typechecks the primary files. Every prerequisite must exit 0; the primary exit and addressed diagnostics are recorded alongside the Court exit and answer. The minimal re-export question deliberately has no judged equality: its legacy answer is unsupported/empty demand, and its complete context/2 answer is `empty`, never `holds`.

The native compiler judges the declared equalities and conformances. The manifest driver is physical-runner debt: matching this finite suite is not a proof of complete Swift equivalence. The reader's export/binding projection is source-reader debt; see the T0105 removal entry in `Contracts/Checks/context-names-v1.md`.

## Owner scopes · T0105 revision 2

`owners.json` is the separate immutable release `vi.court.context-owners/1`, beside the unchanged module-name release. Its context/2 cases distinguish a module's type from a protocol's associated type and from a nested type. The declaration index keys each name with its lexical owner, using the shared scalar identity. Lookup retains the enclosing owner's axes, parameters and member names before consulting module imports. A concrete `Binding.Axis` selects Binding's definition. Two declarations under one owner and missing concrete members refuse at their original source addresses. The existing bounded nested-enum notation remains the admitted nominal fragment; these observations do not admit all nested Swift declarations.

A context/2 definition may lend an empty implementation extension of a supplied nested type after DefinitionView has excluded value bodies. Declaration-bearing or constrained qualified extensions remain unsupported. A borrowed, unapplied generic alias with a qualified bound application is explicitly unchecked at its source address. Its application context is not inferred: the existing conditional-declaration admission barrier rejects any use of that alias as a reduction premise. The three generic-alias cases distinguish an unused definition, an applied valid argument and an applied invalid argument; only the unused definition accompanies a positive question. Complete generic alias applicability is not claimed.

The new declared equalities and conformances use the same Swift/Court contract host. Its process and source-to-owner projections retain the open T0105-R/T0105-C entries; no additional equality of names, identifier grammar or consumer-specific rule is introduced.

`owner-views.json` independently freezes the coordinate relation as `vi.court.context-owner-views/1`. Lexical owners and reference tokens are read from the same line-preserving declaration view; the context hash still binds the original source. Comment width and LF/CRLF byte width cannot move a token into another owner's coordinates by this construction. Native positive and false gates check that relation at the view boundary; these observations do not replace a source-binding derivation.

`owner-members.json` freezes four native-negative contexts as `vi.court.context-owner-members/1`: an absent protocol member, the same projection through an alias, an unread nominal owner's member, and an associated slot projected from an unbound protocol. A supplied owner without a read member definition cannot lend an opaque equality leaf. Source.memberDefinition makes that decision once for tree reduction, DAG reduction and the addressed preparation check; aliases retain it when their owner is normalized. This is an admission requirement, not an additional equation of definitional reduction.
