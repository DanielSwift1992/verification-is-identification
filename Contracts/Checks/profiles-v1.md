# Check profiles before the package split

`python3 Checks/profiles.py --list` lists four profiles and checks that every law registered by `check.sh --list` is assigned. A new or missing law makes selection fail until its owner is named. Commands remain in `check.sh`; the profile driver invokes each named law through that entry point. The `verdict` law has two explicit scopes, bound to the exact supported registry command `bash Checks/verdict.sh`; an executor change requires another reviewed partition.

| Profile | What it asks | Remaining shared dependencies |
| --- | --- | --- |
| `vi` | Core positive certificates and every non-publication refusal; lattice names, Topics, paper families and quotations | Existing Swift package, Tools and plugins |
| `showcase` | Publication positives and all seven `PUBLICATION_*` refusals; demo rules, regenerated artifacts and the organizational differential judge | Current core and showcase source in one pinned checkout |
| `court` | Actual library consumer; existing where/count controls, finite contract and structured response/admission controls | Tools build and current example fixtures; this is the registered acceptance set, not general equivalence |
| `integration` | Whole-package build/tests; repository census, voice, README, grammar and check-driver controls | The whole repository, including showcase targets |

`bash Checks/verdict.sh core` builds Examples and GrammarLexicon and omits exactly `Sources/DocumentKitDemo/Claim.swift` and `Checks/Publication.swift` from the combined positive invocation. It skips exactly the seven flags starting `PUBLICATION_`. The publication scope retains both source files and its existing positive-before-negative checks. Compiler crashes, missing modules and unrelated diagnostics still do not count as refusals. These two scopes cover the same fixture files and mutation flags as `all`; separate positive compilations do not establish the same cross-file interaction check. The unchanged default `./check.sh` and `--only verdict` still run the combined `all` scope and remain the publication gates. Profiles do not replace them.

To measure a profile, use `python3 Checks/profiles.py --profile court --output /absolute/new/evidence-directory`. The driver takes a per-checkout profile lock, captures a clean commit and reads and validates the registry inside that lock. It checks the same commit and clean status after reading and before every command. An earlier listing is never passed into a measurement. It refuses an existing output directory. It records the exact commit, registry hash, commands, Swift version, platform, start time, each command's elapsed wall time, exit status and log hash, plus the final checkout status. It stops on the first failed law. A dirty or changed checkout at completion cannot yield a successful measurement. A partial or interrupted run is not a passing profile. The lock prevents a second profile driver in that checkout; it does not coordinate other tools, so measurements must be scheduled without another build or check running on the machine.

Caches are retained and reported, not cleared. A first run in a new checkout is not necessarily cold because Swift and plugin caches may be shared. Measure profiles sequentially, retain order and host conditions, and compare only stated equivalent conditions. These profiles group verification obligations before extraction; their durations do not measure independent package build costs. Moving targets and tests still requires pinned core/showcase dependencies and another acceptance run.
